# WM-02 — Owner net worth read contract

**Status: WM-02 complete (backend forward-history and mobile partial assessment).** Current owner assessments now materialize durable daily observations. Previously captured days are readable; dates without observations remain explicitly unavailable. Full `net_worth` remains null pending WM-06 liabilities/receivables, as permitted by the PRD.

## Mobile API

`GET /api/v1/net-worth/snapshots?currency=IDR&date=2026-10-20`

Requires access Bearer JWT and active Redis session; no extra RBAC permission. Strict query: optional `currency` (uppercase three letters, defaults IDR), optional real UTC calendar `date` (YYYY-MM-DD, defaults today). Unknown keys, repeated values, invalid dates and future dates return 422. No user/group/account selector is accepted. Standard ApiResponse success envelope (`total_data: 1`, object `data`), Indonesian message, `Cache-Control: no-store`.

Position reasons: `price_missing`, `instrument_unavailable`, `currency_mismatch`, `invalid_position`. Unavailable positions have null valuation and price metadata. Actual zero holdings are omitted and require no quote. Stale means the underlying price date is **before** the requested date (conservative calendar-day rule, not a trading-calendar SLA); stale prices remain in the known subtotal and must be visibly labeled. Manual quote source/date is returned, never replaced by snapshot generation date.

### Date and evidence semantics

Today remains a **live computed read assessment** from committed recorded balances and positions in one RepeatableRead snapshot. GET also inserts derived observation evidence, not a financial mutation. It persists the exact consolidated DTO (only `balance_basis` becomes `captured_recorded_ledger`) and its original `observed_at`. The UTC date is resolved at observation start. This is point-in-time recorded state, **not end-of-day**, an economic effective-date valuation, or a guarantee of coverage every day. Existing future-dated ledger entries remain included in recorded state; latest `price_date <= snapshot_date` is used. `observed_at` is not a quote timestamp.

Storage has a unique `(user_id, currency, snapshot_date)` key. Concurrent inserts use PostgreSQL ON CONFLICT DO NOTHING: the first successful insertion wins, including its full payload/timestamp. Later same-day GETs still return fresh current state but never replace the stored first observation. Late/backdated edits, deletion, changed inclusion flags and price corrections cannot rewrite a capture. The first observation means first successful insertion, not earliest HTTP request start under concurrency. No historical reconstruction, interpolation, scheduled capture, backfill or end-of-day overwrite occurs.

Past dates read only stored owner evidence, returning the original DTO with `balance_basis: captured_recorded_ledger`, original `observed_at`, account eligibility, price metadata and partial limitations intact. Missing dates return 200 with `status: unavailable`, `balance_basis: unavailable`, **all monetary fields null**, empty accounts/holdings and explicit missing evidence. Missing reads never insert rows. Never chart unavailable dates as zero. Stored payloads survive process restarts and are never regenerated from today's accounts. Existing portfolio snapshots are not used to fabricate cash history.

Apply additive migration `20261020120000_net_worth_observations` through the normal reviewed deployment migration step before serving this version; regenerate Prisma client. No persistent database migration/reset is part of development validation. Storage is `net_worth_observations`: UUIDv7 ID, owner FK (restrict deletion), currency, UTC date, observed timestamp, exact JSONB DTO, insertion timestamp. A database check enforces observation UTC day consistency. No sync publication, balance update, ledger entry, investment trade or financial audit mutation occurs. Capture failures fail the GET rather than silently claiming durable evidence.

## Verified balance semantics

- `transactions/ledger.ts` recomputes stored `Account.balance` from current live income/expense and validated signed transfer legs, without separate opening/adjustment evidence.
- `investments/investment.repository.ts` writes a linked CASH expense for BUY (gross + fee) or income for SELL (gross - fee). Only that CASH ledger is recomputed. The INVESTMENT account balance is **not** set to market value.
- Therefore sum eligible ledger balances once (including any INVESTMENT ledger cash) and add market-valued holdings once. Do not add trade gross/cost basis, linked settlement rows or dividend amounts again.
- Legacy unlinked trades exist; they do not imply cash movements. This read reports persisted records, not fabricated settlement/cash adjustments.
- Position quantity is live BUY quantity minus SELL quantity per account/instrument; DIVIDEND does not change quantity. Values are quantity × actual manual price, each position rounded half-up to cents. Decimal arithmetic uses 80-digit precision, never Number. Totals are exact decimal strings and may exceed a single row's numeric range.

## Scope, privacy and limitations

- Both account.userId and accountType.userId must match the principal; account/type/user active filters apply. Own accounts shared to a household remain owned and counted once. Other household members' shared accounts are never queried or returned. This endpoint is intentionally narrower than the dashboard's accessible-account cashflow view.
- Require `is_include_total` and no active children. Exclude parents defensively even if an old parent flag is true. Children are independent ledger balances, not a second copy of a parent total. Deleted accounts/types, opted-out leaves and non-requested currencies do not participate.
- The backend classifies only CASH/INVESTMENT, not complete assets/liabilities. Negative ledger balances are known balance liabilities only; positive balances are not assumed to be receivables. Debt, credit-card classification, receivables, external/manual assets and attribution remain unsupported. `net_worth: null` is deliberate even when all holdings are priced.
- Historical reads require the current active JWT identity/session, not capture-time group membership. Storage lookup requires owner ID, currency, date and currently active/non-deleted owner. Stored payload contains owner-only financial data; no household membership, share grants, names or another owner's accounts. Later account deletion does not revoke the active owner's own old evidence. No shared-history selector exists.
- No HTTP cache, new permissions or dependencies. Derived storage is append-only through this API; no update/delete route or sync publication. Scope bounded at 1000 owner currency accounts and 10000 grouped position rows; overflow returns safe 422 instead of silently truncating totals. Retention is indefinite; no automatic purge is introduced.
- Unit/HTTP tests cover decimal precision, missing/stale valuation, settlement/transfer invariance, owner boundaries and unavailable history. Isolated PostgreSQL tests exercise actual migrated persistence, first-write concurrency, immutable late changes, owner/currency/day scoping, current-active identity and absence of financial/sync writes.
