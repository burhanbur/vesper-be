# Vesper implementation status

## Phase 1 delivered: PRD module 5.1 only

- `GET /api/v1/me`: current-user profile; missing profiles return nullable personal fields/timestamps, `IDR`, and `system` without writing to the database.
- `PATCH /api/v1/me`: strict, non-empty partial update of `full_name`, `phone_number`, `gender`, `photo`, `base_currency`, `theme`. First update creates the profile. Nullable personal fields can be cleared; omitted fields remain unchanged. Soft-deleted profiles are not restored.
- `GET /api/v1/devices`: owner-only pagination (`page=1`, `limit=20`, maximum 100; `sort=created_at|-created_at`, default descending), with stable ID tie-break ordering.
- `POST /api/v1/devices`: name, platform (`Web`, `iOS`, `Android`), app version, optional client UUID. New registration returns 201; retries with an owned UUID return 200 and refresh metadata/last-seen time. Foreign-owned UUIDs return generic 409 without exposing their owner. Omit the UUID only when retry idempotency is not needed.
- Existing JWT authentication checks the exact Redis session and current active/non-deleted database user; no RBAC permissions are required. Existing User/auth contracts remain unchanged.
- All DTOs use snake_case and ISO UTC entity timestamps. Bigint sync cursors are decimal strings. The shared response envelope retains its existing timestamp format.
- Optional `profileRepository` and `deviceRepository` injection mirrors files; omitted dependencies do not mount these routes. Default production dependencies instantiate both Prisma repositories.
- OpenAPI uses the same Zod contracts as runtime validation. No new dependencies or Redis cache keys.

## Photo policy

`photo` is an owned, non-deleted uploaded file UUID or null, not a remote URL, storage path, or data URI. PATCH checks the existing stored-file owner and JPEG/PNG/WebP MIME type inside its database transaction. Existing upload signature/size checks remain in the files module. This endpoint never fetches remote images or grants file permissions. Existing file upload/download routes still require their existing RBAC permissions; an end-user upload/delivery policy is a future product decision, not silently relaxed here. File deletion is not cascaded into profile references in this phase; clients must tolerate unavailable photos.

## Migration and scope boundaries

Additive migration: `prisma/migrations/20261004000000_add_profiles_and_devices/migration.sql`. It introduces only the ERD profile/device columns, enum, constraints, indexes, and user foreign keys. The profile primary key already indexes its user foreign key. Required application fields and bounded strings refine the otherwise unspecified ERD nullability/lengths. Gender database values match the ERD; theme defaults to `system`. Existing authentication uses `User.status`, not an added `is_active` column.

The migration is **not applied** by this implementation. Deploy it explicitly before enabling these endpoints. No tests were added or run, per request; concurrency and migration execution have not been runtime-tested.

Profile sync/change tracking is **deferred until module 5.10**. No profile version, sync_changes, push/pull, conflict reconciliation, or fan-out is implemented. Device registration never writes `last_sync_version` or `last_sync_at`; only the future server sync workflow may advance them. Initial cursor is `0` and last sync is null. Registration is not proof that a device has synced.

## Phase 3 delivered: PRD module 5.3 owner-only scope

Filters: `account_type_id`, `parent_account_id` (UUID for direct children, literal `null` for roots, omitted for all), `is_visible=true|false`.
- Strict snake_case contracts reject unknown fields and client balance/IDs. Server UUIDv7 and initial version `"1"`; creation balance `"0.00"`, never editable. Currency is IDR only. Nullable icon (max 120), description (max 5000), parent; default visible/include_total true and sequence_order `"0"`. Money has two decimal places; version/order are bounded bigint decimal strings; entity timestamps are UTC ISO strings. POST retries are not idempotent.
- PATCH requires a version and at least one editable field; DELETE requires query `?version=1`. Missing/deleted/foreign-owned targets return 404. Stale/exhausted versions return 409 with safe owned DTO in `errors.server_data`. Related-parent version exhaustion may return that owned parent DTO. No response exposes another user's record.
- Parent must be active, owned and same type; self-parent/cycles are rejected. Type changes are disallowed whenever the account has active direct children, maintaining descendant compatibility. Explicit total inclusion is allowed only for leaves.
- Every hierarchy write first takes a transaction-scoped per-owner PostgreSQL advisory lock via bound `hashtextextended(userId, 0)` SQL, then referenced account-type row locks before validation. This serializes owner hierarchy changes and prevents competing reparent/delete/create races, while sharing the account-type category/deletion lock protocol. Hash collisions only cause additional serialization. Future transaction/sync/group writers must participate in this protocol and preserve lock order.
- Attaching a child automatically sets the new parent's `is_include_total=false`; if changed, its version increments in the same transaction. The former parent stays false on reparent/delete; explicitly PATCH a leaf to restore inclusion. Parent/child balances are never rewritten or rolled up; frontend header aggregation remains presentation logic.
- Deletion is soft, increments version, rejects active children, nonzero balance and active transaction references even at zero net balance, and never cascades. Phase 5 adds atomic ledger recomputation and coordinated locks; changing an account type is blocked by any historical ledger reference, including deleted transactions. Optional balance history remains deferred.
- Additive migration `prisma/migrations/20261004020000_add_accounts/migration.sql` adds only accounts, explicit restrictive user/type/self FKs, filter/reference indexes, finite decimal balance, IDR, positive version/nonnegative order and self-parent checks. Nullable icon/description/parent match the ERD; bounded strings and required fields refine unspecified constraints. **Migration not applied.** Deploy all pending migrations explicitly before enabling routes.
- PRD explicitly requires accounts.version despite its original ERD omission; add bigint default 1 and update the ERD additively. Other specification discrepancies remain for later review.
- Optional `accountRepository` DI follows existing modules; defaults instantiate Prisma. Shared Zod OpenAPI documents all four endpoints. No dependencies, cache keys, tests, groups or transactions infrastructure were added. No tests run; migrations, live concurrency and runtime database behavior remain unverified.
- Accounts change publication, sync push/pull, global cursors and fan-out remain deferred to module 5.10. Local optimistic versioning is not offline synchronization.

## Phase 5 delivered: PRD module 5.5 owner-only Transactions

- Seven conventional module files implement authenticated `GET/POST /api/v1/transactions` and `PATCH/DELETE /api/v1/transactions/:id`, optional repository DI and default Prisma wiring. No extra module, dependency or test was added. No tests run.
- Access requires an active account and active type, with both account.user_id and account_types.user_id matching the current user. Authorization never uses created_by as owner. Shared access/category lookup across actors awaits Groups (5.9); no end-user RBAC is added.
- Strict snake_case manual contracts accept INCOME/EXPENSE only. Positive amount is a STRING with up to 18 integer digits and 2 fractional digits (decimal(20,2)); no JSON numbers, floats, exponent/sign/leading zeros. Category UUID is mandatory and must be active, owned by account_types.user_id, and match the transaction type. Description is omitted/null or trimmed nonempty text (max 5000). Transacted timestamps require ISO timezone and milliseconds, serialize as UTC. Server UUIDv7, created_by/updated_by actor, initial version "1"; client IDs, balance, transfer_id and audit fields rejected. POST retries are not idempotent.
- GET has optional exact account_id, category_id, type and inclusive `date_range=start,end` timestamps, page=1/max 1000000, limit=20/max 100, sort created_at|-created_at|transacted_at|-transacted_at (default -transacted_at) and stable ID tie-break. List/count use one repeatable-read snapshot; deleted transactions and inactive/deleted accounts/types excluded. Historical deleted category references remain visible.
- PATCH requires bounded positive bigint STRING version plus at least one editable field; validates merged account/category/type/amount/date/description, including retained fields. DELETE takes query `?version=1`, soft-deletes with deleted_by and updated_by, increments version and does not require a still-active category. Missing/deleted/foreign transactions yield 404. Stale/exhausted versions or linked transfer mutations yield 409 with latest owned active transaction in errors.server_data.
- Every ledger write takes the exact Accounts per-owner transaction-scoped advisory lock first, then sorted account-type IDs, sorted account IDs, sorted category IDs and the transaction row. Accounts, Account Types and Categories mutation paths participate in owner-first locking. References are revalidated after row locks; mutation predicates compare versions (CAS). Future sync/group/transfer writers must preserve this protocol, including deterministic multi-owner locking for cross-owner operations.
- Ledger insertion/update/deletion and account recomputation commit atomically. Every affected old/new account uses live SUM(INCOME)-SUM(EXPENSE) over non-deleted rows and Prisma.Decimal; no floating money arithmetic or balance delta. Balance may be negative, magnitude max 999999999999999999.99. Account balance is server-only; version increments only when the balance actually changes. Overflow/exhausted account version yields 409 with affected safe Account in errors.server_data, rolling back the whole ledger write. Parent totals are not rolled up.
- Category type changes reject every historical ledger reference (including deleted); account reassignment rejects every historical reference; account deletion rejects active ledger rows even at net zero. Category soft deletion preserves references and forbids new/merged writes to the deleted category.
- Additive migration `20261004040000_add_transactions` adds mapped transaction enum/table, restrictive indexed account/category/actor FKs, amount/version/description checks and audit timestamps. Nullable transfer_id UUID has **no FK yet**, because Transfers does not exist. TRANSFER is reserved in persistence/read contracts, rejected in direct POST/PATCH, and any linked transfer row is protected from manual PATCH/DELETE. Phase 6 adds the real transfer FK and paired signed TRANSFER rows (negative source, positive destination); direct manual writes remain INCOME/EXPENSE only.
- Migration **not applied**. Safe Prisma generation only; deploy all pending additive migrations explicitly before using these routes. Live database concurrency, migration execution and runtime ledger behavior remain unverified. No database tests, resets or data mutations performed.
- Full shared Zod OpenAPI documents filters, bodies, success envelopes, pagination, validation/authentication/not-found/conflict/rate-limit/server failures and examples. Sync publication/cursors/fan-out (5.10), groups (5.9), investment-derived ledger writers (5.8) and optional account balance history remain deferred. Investment nullable categories require future integration rules; manual writes currently require categories. Local optimistic versions do not implement offline synchronization.

## Phase 7 delivered: PRD module 5.7 owner-only Budgets

- Authenticated `GET/POST /api/v1/budgets`, `PATCH/DELETE /api/v1/budgets/:id`, and `GET /api/v1/budgets/:id/progress?period=...` use optional repository DI and shared Zod OpenAPI. DELETE returns 204. No budget name, owner column or version is invented; ownership resolves through the active category. Income and expense categories are both allowed.
- Strict snake_case input: UUID category, calendar anchor_date, MONTHLY/WEEKLY/DAILY/ANNUAL, IDR base_currency, optional nullable icon/description, signed bigint STRING sequence_order, positive decimal(20,2) STRING amount. List supports category_id/period_type, page/limit (max 100), created_at/sequence_order ascending or descending and stable ID tie-break. DTO includes latest open current_amount, not the historical allowance.
- Category, anchor_date and period_type are immutable after creation: changing them returns 409 with an Indonesian explanation to create a new budget. This intentionally narrows the generic PRD edit form to preserve historical interpretation. Metadata and amount remain editable. Category type changes also reject historical budget references. Deleted categories hide budgets; budget DELETE retains all amount history.
- Every mutation takes the existing per-owner advisory lock first, then budget/category row locks with final active ownership validation. Creation and amount changes are atomic. Each amount PATCH closes the open row at today UTC and inserts a new effective row starting today UTC. Amount values are never overwritten. Half-open `[effective_from,effective_to)` intervals retain same-day zero-duration audit rows without counting them in progress. No optimistic version exists in the ERD; concurrent metadata changes serialize but remain last-writer-wins.
- Shared `src/common/utils/budget-period.ts` calculates host-timezone-independent UTC half-open ranges. Monthly YYYY-MM identifies the start month and clamps the anchor day independently at each boundary (including day 31). Annual YYYY identifies the start year and clamps February 29. Weekly YYYY-MM-DD identifies a containing day and starts on the anchor weekday on/before it. Daily YYYY-MM-DD starts at UTC midnight. Anchor dates define recurrence, not an activation cutoff; amount effective dates define funded days.
- List/count and progress use repeatable-read snapshots. Progress sums live transactions matching category AND category type over the whole period, excluding TRANSFER and all linked transfers. Accounts and account types must be active and owned by the same user; accounts must use IDR. No authorization through actor IDs or shared groups.
- Explicit overlap policy: each positive-duration segment contributes `amount * active UTC days / period UTC days`, rounded HALF_UP to cents per segment and summed. Mid-period creation funds only active days. Progress returns segment dates, original effective dates, active_days, segment allowance, total_amount, summed allowance, remaining_amount and uncapped progress_percent as two-place decimal strings. Zero allowance means null percentage. Money uses Decimal, never Number; UTC day counts are integers. Past amount values are retained, but backdated transaction edits can change historical spending totals.
- Additive migration `20261004060000_add_budgets` adds mapped PeriodType, Budget and BudgetAmount, restrictive indexed FKs, positive amount/date/IDR checks, and one-open-row partial unique index. **Not applied**. No new dependency, tests, cache, groups or sync implementation. Live migration/concurrency behavior remains unverified; deploy pending migrations explicitly before using budgets.

## Phase 8 delivered: PRD module 5.8 Investments

- Seven endpoints: GET/POST `/api/v1/instruments`, GET/POST `/api/v1/instrument-prices`, POST `/api/v1/investment-transactions`, GET `/api/v1/accounts/:id/holdings`, GET `/api/v1/accounts/:id/portfolio-snapshot?date=YYYY-MM-DD`. Optional investment repository DI, default Prisma wiring, shared Zod runtime/OpenAPI contracts. Existing edits are preserved.
- JWT, exact active session and active user required, no RBAC. Global instruments and manual prices are shared facts; any authenticated user can create/update them. Private investment accounts require active owned accounts and active owned INVESTMENT types; optional cash accounts require distinct active owned CASH accounts. Groups remain deferred to 5.9. All currencies must be IDR; no FX or Redis price cache.
- Instrument code is uppercase, globally DB-unique even across deleted records. List/search uses case-insensitive code/name substrings, page/limit (max 100), code ascending/descending. Price listing supports instrument_id and exact price_date, page/limit, price_date ascending/descending. Stable ID tie-breaks and repeatable-read list/count. Instrument POST returns 201; price POST upserts `(instrument_id, price_date)` and returns 200 for both insert/update, with source MANUAL and actor updated_by.
- Exact ERD columns, mapped enums and scales: quantity, price_per_unit, close_price and snapshot quantity/average/market price decimal(20,8); fee, realized_pl, market_value and unrealized_pl decimal(20,2). Strict decimal STRING input rejects numbers, signs, exponents, excess digits and leading zeros. Quantity/prices positive; fee nonnegative. Required instrument currency IDR. Safe explicit DTOs use fixed-scale strings, bigint version strings and ISO UTC timestamps; no user secrets are selected.
- POST-only investment transactions receive UUIDv7, version 1 and actor audit IDs. Timestamp supports timezone and at most millisecond precision. **Chronological-write policy:** every BUY/SELL/DIVIDEND timestamp must be strictly later than the latest historical transaction for that account/instrument; backdated/equal writes return 409. No edit/delete route or silent subsequent realized P/L rewrite. POST retries are not idempotent.
- Moving weighted average of remaining purchases excludes BUY fees; partial SELL retains average, liquidation resets it to zero, subsequent BUY starts afresh. Oversell returns 409. Only SELL sets realized P/L: `quantity * (price_per_unit - moving_average) - fee`. DIVIDEND uses `quantity * price_per_unit` as gross entitlement and does not change holding units; cash-null does not implicitly reinvest units. An actual reinvestment requires a separate BUY.
- Optional cash creates exactly one category-null ledger transaction with a restrictive linked FK: BUY EXPENSE `quantity * price + fee`; SELL/DIVIDEND INCOME `quantity * price - fee`. HALF_UP cents rounding; linked net must be positive after rounding. Cash-null creates no ledger row. Decimal arithmetic uses 80-digit precision, persisted numeric bounds are checked; overflow or any downstream failure rolls back the whole transaction. Only cash ledger balances are recomputed via the shared helper; investment account balance is never market value. Linked investment cash rows cannot be manually patched/deleted. Account type reassignment and deletion are blocked by all investment history (including cash-null/deleted references) or snapshots; account-type category changes already reject referenced accounts.
- Every price/investment writer first locks the same global instrument advisory key. Investment writes then take existing owner advisory, sorted type/account locks and revalidate ownership/category/currency; no nested transactions. Cross-user price regeneration does not write account balances or take owner locks, avoiding reversed lock ordering. Price responses expose no other users' account/snapshot IDs.
- Snapshots replay history strictly before the next UTC day and select the last price on/before the requested date. Price upsert synchronously refreshes that day for every historical account/instrument and later stored snapshots (including fallback-price dependencies). Investment POST refreshes all affected existing price dates and stored snapshots from its UTC day onward. Zero holdings are retained as zero snapshots; no price means nullable valuation in the GET fallback, not fabricated zero. Snapshot GET reads stored values where available, otherwise computes on-the-fly without writes. Reads use RepeatableRead.
- Regeneration and history replay use paginated batches (100 accounts/dates, 250 transaction rows). This bounds query memory, not total transaction work: MVP regeneration is synchronous with a 60-second transaction timeout and 10-second lock-acquisition wait. Large histories may time out and roll back entirely; there is no background job/outbox yet. Account holdings responses themselves are not paginated, per PRD. Larger-scale background regeneration remains an explicit follow-up.
- Additive migration `20261004070000_add_investments` adds only instruments, prices, investment transactions and daily snapshots with restrictive FKs, uniqueness, indexes and numeric/cash/type checks. **Not applied**. Deploy pending migrations explicitly before using these routes. No dependencies, tests or database mutations added/run; migration execution and runtime/concurrency behavior remain unverified. No investment sync publication: online-only scope is explicit per PRD 5.10/8.

## Phase 9 delivered: PRD module 5.9 Groups and shared finance access

This phase supersedes the owner-only/shared-access deferrals in Phases 3–6 and 8 above. Budgets remain owner-only.

- Authenticated group routes cover create/list, join, paginated members and categories, share/unshare accounts, OWNER-only group category create/update/delete, personal category map/unmap, and monthly category reports. Optional group repository injection and default Prisma wiring follow existing modules; runtime Zod schemas also define OpenAPI contracts. Group responses send `Cache-Control: no-store`.
- Group creation atomically creates OWNER membership and a cryptographically random 12-character uppercase hexadecimal join code (48-bit entropy); unique-code collisions retry at most five times. The code is returned only on creation, omitted from lists, and redacted from request logs. Join verifies both the requested group ID and exact code against an active/non-deleted group, returns generic denial on failure, and is idempotent without escalating roles or demoting an OWNER. Join attempts are limited to 10 per IP per 15 minutes **per process**, not a distributed Redis limit.
- Membership gates group reads and writes: requester and listed members must be active/non-deleted users, and the group must be active/non-deleted. Only OWNER membership can mutate group categories. Active members can share/unshare only their own active accounts with their own active types, and map/unmap only their own active personal categories of the matching group-category type. Same mapping retries are idempotent; competing mappings return 409. Mapping uniqueness and composite same-group category foreign keys prevent cross-group references. Group category deletion removes mappings atomically, not personal history.
- Accounts and transaction lists use owned OR explicitly shared account access through active joined groups, with active/non-deleted account types and owners. Category lists optionally accept `account_id`, check account access, and return that account-type owner's active categories; arbitrary owner selectors are not accepted. Account metadata/hierarchy and personal category mutations remain owner-only. Transaction validation uses the account-type **owner**, not the acting group member, while audit fields identify the actor.
- Transfers require both distinct source and destination accounts to be active and accessible, with IDR currency, before atomic paired ledger writes. Investment holdings/snapshot reads and investment/cash writes use the same shared-access policy with INVESTMENT/CASH type checks; no account metadata ownership privilege is granted by sharing.
- Shared ledger and investment writes lock sorted distinct **actual account owners**, then sorted group/membership/share grants with SHARE row locks, then sorted account types/accounts and applicable category/transaction rows. Access is revalidated after locks under ReadCommitted. Investment writes take the global instrument advisory lock before this ledger protocol. Group grant writers take the owner lock where applicable before the group UPDATE lock, coordinating share revocation; future membership/deactivation writers must participate in this protocol. No leave, member removal, role management, group edit/deactivation or join-code rotation endpoints are implemented.
- Category reports aggregate decimal-string income/expense for a UTC calendar month using a repeatable-read snapshot. Only live transactions on accounts shared **in the requested group**, active owner membership, same-group mappings, and matching account/category owner and type count. Private accounts, soft-deleted resources, TRANSFER, investment-linked cash transactions and category-null rows are excluded. Current mappings can reclassify historical transactions; there is no historical mapping snapshot or FX conversion.
- Transfer/transaction DTOs currently expose account UUID references, not counterpart account names. **No name serialization/privacy masking is implemented or claimed.** Members intentionally receive member names/profile fields and owner categories for accessible accounts; shared ledger descriptions and safe DTO fields are not selectively redacted.
- Additive migration `prisma/migrations/20261004080000_add_groups/migration.sql` introduces groups, membership, shares, group categories and mappings with restrictive foreign keys, uniqueness, checks and indexes. **Migration not applied**; deploy pending migrations explicitly before using these routes. No tests or migrations run for this phase. Live concurrency, report correctness against a real database, migration execution and security behavior remain runtime-unverified. No new dependency, cache key, sync publication or notification fan-out is added.

## Phase 10 delivered: PRD module 5.10 Sync Engine

- Authenticated device-bound push/pull for account types, accounts, categories, transactions, and profiles. Push applies each item atomically through the existing mutation rules, accepts client UUIDs, and reports applied/conflict/rejected outcomes.
- Atomic REST-write publication, shared-account fan-out, and join/share/unshare snapshots or visibility tombstones are integrated. A global transaction lock preserves event commit ordering; pull returns latest authorized payloads and bounded cursor pages.

## Phase 12 — Auth Registration (PRD 4)

- `POST /api/v1/auth/register` creates an active user with Argon2id-hashed password, auto-assigns the default `User` role if present in the database, and returns HTTP 201 with initial access/refresh JWT tokens and revocable Redis session.
- Validates name (2–120 chars), optional username (3–64 chars lowercase), email, and password (8–128 chars). Rejects duplicates with 409 Conflict (`EMAIL_ALREADY_EXISTS` or `USERNAME_ALREADY_EXISTS`).
- Protected by registration rate limiting matching login window/limits.
- Fully documented in OpenAPI specification with representative responses.

## Phase 13 — Machine-to-Machine API Keys (PRD 4)

- `api_keys` table and Prisma model with 64-character hex key, metadata (`name`, `description`, `application`), JSON arrays for `ip_whitelist` and `permissions`, `is_active`, `rate_limit`, `last_used_at`, and `expires_at`.

- Management endpoints under `/api/v1/api-keys`:
  - `GET /api/v1/api-keys`: Paginated listing with filtering.
  - `POST /api/v1/api-keys`: Secure key generation (random 64-character hex string) returned only once.
  - `GET /api/v1/api-keys/:id`: Retrieve key metadata without exposing the secret.
  - `PATCH /api/v1/api-keys/:id`: Partial update of metadata, IP whitelist, permissions, or revocation.

  - `GET /api/v1/api-keys/verify`: Protected by `X-API-Key` to verify credentials and return authenticated principal information.
